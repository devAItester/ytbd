# Жизненный цикл данных YouTube

## Принцип

Сбор, архивирование и Markdown-вывод — отдельные этапы. Неудачный запрос не должен заменять последний успешный исходный ответ или удалять ранее найденные записи. Шаблоны можно менять независимо от сбора.

## Фактическая структура сборщика

```text
config/channels.txt
templates/
  outline.md
  archive.md
  index.md
  full.md
data/
  channels/<handle>/
    channel.json
    raw/
      channel.json
      videos.json
      streams.json
      podcasts.json
      playlists.json
      history/<source>/<sha256>.json
    archive/
      videos.json
      streams.json
      podcasts.json
      playlists.json
    status.json
    logs/
  output/<handle>/<template>.md
```

- **channel.json** — последний успешно полученный ответ с метаданными канала.
- **raw/** — последние успешные ответы по каждой вкладке.
- **raw/history/** — содержимое отличающихся успешных ответов, адресуемое по SHA-256. Одинаковые ответы не сохраняются повторно.
- **archive/** — накопленные записи каждой вкладки. Новые записи добавляются, совпадающие идентификаторы обновляются, отсутствующие в текущем списке записи сохраняются.
- **status.json** — время проверки, статус каналов и вкладок, счётчики и ошибки.
- **logs/** — диагностика неудачных сетевых запросов, если она была получена.
- **data/output/** — Markdown, сформированный выбранным шаблоном из локального архива.

## Последовательность одного запуска

1. Прочитать все уникальные URL из config/channels.txt; пропустить пустые строки и комментарии.
2. Получить метаданные канала и плоские списки видео, трансляций, подкастов и плейлистов.
3. Принимать новый JSON только при успешном завершении yt-dlp и ожидаемой структуре ответа.
4. При успехе сохранить текущий исходный ответ и историческую копию, если её содержимого ещё нет.
5. Сопоставить записи по идентификатору, обновить найденные метаданные и добавить новые. Не удалять архивные записи только потому, что их нет в текущем ответе.
6. Если отдельный источник недоступен или ответ некорректен, сохранить предыдущие данные, записать ошибку и продолжить другие вкладки и каналы.
7. Построить Markdown из локального архива по выбранному Jinja-шаблону.

## Что означает инкрементальность

При каждом запуске выполняется сетевой запрос для проверки актуальности списков. Это необходимо, чтобы обнаружить новые записи и изменения. Однако неизменившиеся JSON-файлы и исторические снимки не перезаписываются; повторяющиеся записи не добавляются второй раз в архив.

Сборщик получает плоские метаданные для навигационных списков и, при выборе full.md, отдельно запрашивает подробные метаданные каждого обрабатываемого видео. С --download-media дополнительно сохраняются доступные обложки, субтитры ru/en и текстовые транскрипты; сами видеофайлы не скачиваются. Комментарии не собираются. Полнота списка зависит от доступности и поведения YouTube/yt-dlp. Полное описание API-методов и различий с YouTube Data API приведено в youtube-data-api-comparison.md.

## Проверки и ограничения

- Автоматические тесты работают на локальных фикстурах и не требуют доступа к YouTube.
- Сетевая проверка нужна отдельно для подтверждения работы источника в GitHub Actions.
- Ошибка одного раздела не должна удалять его предыдущие данные или прерывать остальные разделы.
- Пропавшие из текущего списка записи сохраняются в архиве; автоматическое окончательное удаление не выполняется.
- JSON исходных ответов сохраняется отдельно от накопленного архива и Markdown-представления.
